
# VENORA MVP Database Schema

## 1. Overview

This document defines the MongoDB schema for the first working prototype of VENORA.

The MVP uses three main collections:

1. Users
2. SupplierProfiles
3. Requirements

The schema supports user registration, login, requirement submission, and AI-based supplier matching.

## 2. Users Collection

The Users collection stores the account details of vendors and suppliers.

| Field Name | Data Type | Required | Description |
|---|---|---|---|
| _id | ObjectId | Yes | Unique user ID generated by MongoDB |
| name | String | Yes | Full name of the user |
| email | String | Yes | Email address; must be unique |
| passwordHash | String | Yes | Hashed password; never store a plain-text password |
| role | String | Yes | User role: vendor or supplier |
| createdAt | Date | Yes | Account creation date |
| updatedAt | Date | Yes | Last update date |

**Constraints:**

- Email must be unique.
- Role must be either `vendor` or `supplier`.
- Passwords must be hashed by the backend before storage.

## 3. SupplierProfiles Collection

The SupplierProfiles collection stores supplier details required for matching and comparison.

| Field Name | Data Type | Required | Description |
|---|---|---|---|
| _id | ObjectId | Yes | Unique supplier profile ID |
| userId | ObjectId | Yes | Reference to Users._id |
| companyName | String | Yes | Supplier company name |
| industry | String | Yes | Industry served, such as wood, steel, or textile |
| product | String | Yes | Main product or material supplied |
| pricePerUnit | Number | Yes | Price for one unit, in INR |
| qualityRating | Number | Yes | Supplier quality rating from 1 to 5 |
| deliveryTimeDays | Number | Yes | Estimated delivery time in days |
| location.city | String | Yes | Supplier city |
| location.state | String | Yes | Supplier state |
| isActive | Boolean | Yes | Whether the supplier is active |
| createdAt | Date | Yes | Profile creation date |
| updatedAt | Date | Yes | Last update date |

**Constraints:**

- `userId` references the corresponding user in the Users collection.
- `userId` should be unique for one supplier profile per account.
- `pricePerUnit` must be greater than or equal to zero.
- `qualityRating` must be between 1 and 5.
- `deliveryTimeDays` must be greater than or equal to zero.
- Only active suppliers should be considered for matching.

## 4. Requirements Collection

The Requirements collection stores procurement requirements submitted by vendors.

| Field Name | Data Type | Required | Description |
|---|---|---|---|
| _id | ObjectId | Yes | Unique requirement ID |
| vendorId | ObjectId | Yes | Reference to Users._id |
| industry | String | Yes | Required industry |
| material | String | Yes | Required product or material |
| quantity | Number | Yes | Required quantity |
| budget | Number | Yes | Maximum total budget, in INR |
| location.city | String | Yes | Required delivery city |
| location.state | String | Yes | Required delivery state |
| status | String | Yes | Requirement status; default is open |
| createdAt | Date | Yes | Requirement creation date |
| updatedAt | Date | Yes | Last update date |

**Constraints:**

- `vendorId` references the vendor's account in the Users collection.
- Quantity must be greater than zero.
- Budget must be greater than or equal to zero.
- The status must be one of the agreed values, such as `open`, `matched`, or `closed`.
- The backend should confirm that the submitting user has the vendor role.

## 5. Collection Relationships

1. **Users → SupplierProfiles:** One supplier account can have one supplier profile. The profile's `userId` references `Users._id`.

2. **Users → Requirements:** One vendor can submit multiple requirements. Each requirement's `vendorId` references `Users._id`.

3. **Requirements → SupplierProfiles:** The matching logic compares a requirement with suitable supplier profiles. Matching results may be returned by the API without being permanently stored in a separate collection for this MVP.

## 6. Supplier Matching Fields

The matching process can use these fields:

- Industry
- Required material and supplier product
- Quantity and price per unit
- Total estimated cost
- Budget
- Supplier quality rating
- Delivery time
- Location

The estimated total cost is calculated as:

**Estimated Total Cost = Quantity × Price Per Unit**

The backend can compare this amount with the requirement's total budget and rank suitable suppliers using the agreed matching logic.

## 7. Security and Implementation Notes

- Never store plain-text passwords.
- Never upload database passwords or MongoDB connection strings to GitHub.
- Validate required fields on the backend.
- Use MongoDB ObjectId references for relationships between collections.
- Keep field names consistent across the frontend, backend, and database.
- Confirm the final field names and API formats with the backend developer before integration.

## 8. MVP Scope

This schema supports the initial VENORA prototype for registration, login, requirement submission, supplier matching, and display of the top three supplier results.

Additional collections and advanced features can be introduced in later project versions.
